# Исходное продуктовое ТЗ

Неизменяемая копия продуктового задания. Нормализованные документы и
`docs/decisions.md` уточняют контракт; этот файл не переписывают «чтобы стало удобнее».
Новый явный prompt пользователя старше только если он явно меняет контракт — тогда решение
фиксируют в `docs/decisions.md`, а не правят этот файл.

Демо — вымысел, не кейс клиента.

## Зачем демо

Protostar продаёт не витрину опта. Продаём клиентский канал статуса по не‑SKU заявке
(спецификация под заказ: щит/НКУ/комплект).

Боль, которую должен считать зритель за 30 секунд: запрос нельзя купить карточкой с полки;
заказчик снаружи видит, жива ли заявка и на каком шаге (принят → в расчёте → КП → счёт);
менеджер кидает ссылку, а не просит «завести кабинет».

После просмотра у человека должно сложиться: «вот что увидит мой заказчик по ссылке».
Не платформа, не ERP, не магазин.

Вымышленный завод — новое имя, не «Вольтарис». Вольтарис = другая витрина с каталогом, её
нельзя цитировать как этот продукт.

## Что должно быть на экране

1. Первый экран (служебный, только для демо): список готовых ссылок. Подпись в духе «так
   выглядит то, что вы отправили бы заказчику в мессенджер». Клик = переход в кабинет, как
   по magic link. Ссылки не рассылаем и не копируем вручную.
2. Кабинет «снаружи»: одна заявка по секрету в URL. Этапы, краткая спецификация (не корзина
   SKU), файлы как список (например КП.pdf) без редактора, дата обновления. Без чата, без
   логина, без OTP, без телефона.
3. Несуществующий секрет → понятный тупик, не форма входа.

Сиды: 4–6 заявок в разных статусах и на разных вымышленных контрагентах. На индексной
странице явно: этот список не показывается заказчику.

## Жёсткие границы MVP (нарушение = провал)

Запрещено: каталог/корзина SKU, типы цен, Excel-заказ, оптовый логин и роли, чат, OTP/SMS,
регистрация, оплата, ЭДО, 1С/ERP/CRM как интеграция, универсальная шина заявок, Integration
Lab, mock-api, Redis, брокер, Elasticsearch, Kubernetes, AI, CMS, multi-tenant SaaS,
«безлимитная разработка», уведомления в Telegram, админка менеджера (кроме индексного
списка ссылок), glassmorphism, нейрослоп, bento, неон, 3D-блобы, стоковые иллюстрации
«AI dashboard».

Не копировать предметный код Вольтариса (`apps/web`, `apps/mock-api`, Prisma каталога/RFQ,
Pinia спецификации). Смотреть Вольтарис только как composition root: pnpm workspace, Nest
hexagon, OpenAPI client, Prisma+Postgres, Tailwind `@theme`, Makefile, Docker.

Отдельного mock-процесса нет и не будет: «их система заявок» в демо = Postgres + seed.

## Стек (уже задан заготовкой)

- pnpm workspace, Node/pnpm как в корневом `package.json` / `.nvmrc` (линия 24.18 / pnpm 11).
- `apps/api` NestJS/Fastify на `@client-portal/nestjs-core` + `@client-portal/platform-core`.
- `apps/web` Nuxt, Tailwind v4, `@theme`, server state через `useFetch`/`useAsyncData` и
  generated `packages/api-client`. Web не импортирует Prisma, DTO Nest, `apps/api`.
- OpenAPI: prefix `/api/v1` на server URL, path keys относительные; `pnpm generate:api`,
  руками `openapi.json` / `schema.d.ts` не править.
- PostgreSQL в Docker, Prisma в `apps/api`, миграции, seed.
- Docker Compose для Postgres (и для полного стенда приложений — как recipe Вольтариса,
  имена/порты свои). Lifecycle только через корневой `Makefile` (`bootstrap` / `dev` / `up` /
  `down` / `verify` по факту Makefile), не сырой `pnpm dev` / `docker compose` в инструкциях
  для агентов, кроме skill.
- Слои Nest: skill `nestjs-hexagonal-boundaries`. Prisma: `prisma-persistence-boundary`.
  Nuxt: `nuxt-ssr-data-and-ui`. Ворота: `change-impact-gates`. Отчёт: `verification-honesty`.
  Ветка/PR: `git-delivery`. Ревью: `pr-review`.
- `pnpm check:boundaries` обязателен и не заменяется ESLint.
- Mock-core / mock-api не добавлять.

Порты: не занимать чужой стенд вслепую. Канонический origin web и порты api/db — в
`docs/decisions.md`.

## Дизайн

Консервативно: бумага/off-white, один приглушённый акцент (чернила, сталь, пыльный синий),
одна гротеск-гарнитура с табличными цифрами, чёткая типографика, много воздуха, статусы как
лента документа/штампов, не канбан и не дашборд с графиками. Интерфейс на русском.

Живые референсы, токены и запреты — в `docs/frontend.md` (не картинки из нейросетей).

## Процесс разработки

Каждая фича = один PR с feature-ветки в `main`, в `main` не пушить.

TDD: тесты по приёмке пишут **до** кода продукта. Сначала red (команда и причина падения),
потом минимальная реализация, потом green без подгонки assert. Иначе тесты становятся false
positive. Подробности — `AGENTS.md` и `docs/testing.md`.

После реализации фичи агент:

1. targeted-тесты изменённого поведения (уже написаны на шаге TDD);
2. применимые root gates (имена сверить с корневым `package.json`): как минимум
   `pnpm check:boundaries`, `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm test:packages`,
   `pnpm build`; e2e — когда появится web-сценарий; для контракта — `pnpm generate:api`; для
   Prisma — `pnpm db:generate` и миграция на предназначенной БД;
3. факт запуска и результат — в `docs/implementation-status.md` (skill `verification-honesty`:
   не писать «должно работать»; для фичи — red **и** green);
4. открыть PR;
5. отдельным шагом/чатом — skill `pr-review` (ревью диффа + что CI/команды реально прошли,
   не badge).

Фиктивный UI запрещён: мёртвые кнопки, `#`, декоративные статусы без данных API.

## Нарезка фич

Мало фич, каждая закрывается одним чатом (~один PR). Не дробить «поменять цвет» отдельно от
экрана. Порядок и зависимости — `docs/implementation-plan.md` и `docs/llm/feature-NN.md`.

1. Docker Postgres + Prisma + Makefile db + пустая модель/health ready зависит от БД.
2. Домен заявки + статусы + секрет + seed 4–6 записей + OpenAPI + `packages/api-client`.
3. Nuxt-каркас + токены Tailwind по `frontend.md` + layout + Playwright harness.
4. Экран списка демо-ссылок (чтение API); e2e сценария — до страницы.
5. Кабинет по секрету в URL + 404; e2e сценария — до страницы.
6. Compose-smoke полного стенда и CI e2e, если их ещё нет.

Не тащить в фичи «коннектор к amo/1С», чат, OTP, загрузку файлов с диска (достаточно
метаданных в seed), редактирование статусов в UI.
